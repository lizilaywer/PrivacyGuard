## 1. 为什么没有默认启用字符定位

保留 PP-OCRv6 Small，接入单字符框后，原 24 个合成图像例子中 96 个目标的覆盖改善。随后换用另一组名称、字段布局、字体和字号，扩大至 48 个图像、192 个已知目标：

- 识别到 192/192 个目标；这是这个合成集的结果，不是对法律文书的准确率保证。
- 新候选有 **1 个目标的字形覆盖低于旧算法**，2 个目标未达到完整字形覆盖。
- 非敏感像素误遮计数由 1,368 增至 2,254；不能用其他样本的平均覆盖改善抵消这项退步。
- 因而没有达到发布默认的标准，`RapidOCREngine()` 默认不请求字符框。只有显式开发试验构造参数可启用，没有向用户新增设置。
- 对关闭实验路径的引擎，用稳定版归档中的原始封装逐项比较 8 张合成图像：识别文字、行框、置信度完全一致。热态耗时中位数约 819/802ms，接近测量噪声，不宣称加速。
- 默认关闭不代表旧算法对所有字形已完美覆盖。合成测试同样暴露旧定位的不足，仍需人工复核；后续要补真实分布的授权本机样本、完整字形与误遮对照，候选通过门槛后才可启用。

实现仍保留：源文本偏移、整行严格对齐、缺字符/错行/非有限坐标/低置信度/旋转斜行等回退、用户偏移设置兼容、混合图块坐标平移一次、人名回填缓存与字符缓存预算。默认路径不保存新字符缓存，不额外初始化另一套模型。

`scripts/evaluate_ocr_geometry.py` 用于复现候选；当前 `--cases 48` **预期返回非零**，表示候选被门槛拒绝，不是要求降低断言让它通过。样本是合成变体，不是独立真实文书保留测试集。

## 2. 导出保护的实际行为

独立模块：`privacyguard/utils/export_transaction.py` 与 `export_validation.py`。MainWindow 只改调用接线，既有导出对话框、扫描不完整确认和权限检查保持。

1. 在目标目录创建随机临时文件，不提前清空已有成果。
2. 写出后关闭写入句柄，再重新打开核验。
3. PDF 核对页数、页面尺寸/CropBox/旋转、最终书签、打开密码、编辑权限和加密状态；有遮罩的区域检查非预期的可提取文字。用户指定的替换文本允许保留，文字顺序也要符合要求。
4. Word 核对 ZIP CRC、全部预期 package part 的字节与可解析关系，防止未写全或写出内容偏离意图；批量 Word 使用同一入口。
5. 核验通过后同步文件并进行同卷原子替换。检测到源/目标相同、硬链接指向源、目标已被他人改动、路径变化或替换失败时停止，已有文件不被提前删除。

“同卷原子替换”依赖底层文件系统语义；并不宣称能够抵御同权限恶意进程对任意文件的竞态攻击。临时文件采用系统 mkstemp 权限策略；Windows 仍依赖目标目录 ACL。若外部程序占用导致临时文件清理失败，可能留下一份限制访问的临时输出，不能保证磁盘上绝无残留。

### 验证范围的限制

- PDF 本批不会全面净化附件、元数据、脚本、结构树、表单等对象；不会从头识别所有未知敏感信息。
- 文字目标复查允许用户明确提供的替换文字，不能把这项检查当作完整的内容来源证明。
- 图片遮罩的像素正确性在合成导出语料中验证；运行时复查未增加第二轮全页 OCR，也不能用同一 OCR 二次识别保证零漏识别。
- Word 部件字节一致仅证明“按当前编辑意图写出完整”，不证明当前尚未支持的 XML 内容已经脱敏。超链接/嵌套表格/批注修订等覆盖扩展仍是后续阶段。
- 复查沿用既有导出动作执行，不新增完整的异步导出架构；超大文件的 UI 响应/内存还需专门性能样本，不能据小样本宣称全部场景无阻塞。
- 来源文件保存为新文件是有意的保护；正常新文件导出不增加操作。用户选回输入路径时会得到“另存为新文件”的明确提示。

## 4. 后续阶段

按 `REDACTION_UPGRADE_PLAN_20261118.md` 继续推进，不能把本批成果写成“八项计划全部完成”：

1. 候选定位继续研究：更多本机授权文书、跨行/旋转/小字/噪声/复杂背景及像素对齐；不向用户交付退步的默认路径。
2. PDF 隐藏内容先清点后制定净化策略，防止无提示丢失附件/表单/签名信息。
3. Word 共用 XML 遍历，扫描与写出一致，逐部件补盲。
4. 复核清单作为可收起的辅助面板，保持当前一键处理习惯；再做模板与逐文件规则，不同时重做整个界面。
5. 引擎/模型升级单独对比，保持轻量离线，达到门槛再替换。

本批优先保证原文件与已有成果受保护、导出失败不假成功，并执行“不达标就不默认启用”的决定。
